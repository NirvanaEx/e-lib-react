# Уборка лишнего — e-lib-react — 2026-08-16

## Что сделано

### 1. Удалены два мёртвых layout-компонента
- **Файл:** `apps/web/src/app/layouts/AdminLayout.tsx`, `apps/web/src/app/layouts/ManageLayout.tsx` (удалены целиком)
- **Зачем:** оба компонента не импортируются нигде — `App.tsx` использует только
  `DashboardLayout` и `UserLayout`, которые их заменили. Поиск по всему проекту
  (`grep -rn "ManageLayout\|AdminLayout"` по `apps`, `packages`, `ops`, `scripts`)
  находит только строки их собственных объявлений.
- **Что изменилось для кода:** убрано 48 строк мёртвого кода; в папке `layouts/`
  осталось три реально используемых файла вместо пяти, и при правке навигации
  больше нет риска отредактировать не тот layout.
- **Как проверить:** `cd apps/web && npx vite build` — сборка проходит;
  `grep -rn "AdminLayout\|ManageLayout" apps packages` — пусто.

### 2. Удалён неиспользуемый `userLibraryTableLayouts`
- **Файл:** `apps/web/src/features/files/fileTableLayout.ts:100-245`
- **Зачем:** объект с тремя раскладками таблиц (`files`, `department`,
  `favorites`) не импортируется ни одним файлом. `UserLibraryPage.tsx`, для
  которого он по названию предназначался, его вообще не импортирует;
  реально используются только `adminFilesTableLayout` (в `FilesPage.tsx`) и
  `sharedLibraryTableLayout` (в `UserFilesPage.tsx`).
- **Что изменилось для кода:** убрано 147 строк мёртвого кода, файл
  сократился с 245 до 98 строк. Три почти одинаковые копии одной раскладки,
  различавшиеся только шириной колонки `status` (96/104/64), больше не
  расходятся с живым `sharedLibraryTableLayout` при правках.
- **Как проверить:** `cd apps/web && npx vite build`;
  `grep -rn "userLibraryTableLayouts" apps/web/src` — пусто.

### 3. Убран дублирующий запрос в `GuidesService.listStatuses()`
- **Файл:** `apps/api/src/modules/guides/guides.service.ts:178-186`
- **Зачем:** цикл вызывал `ensureSeeded(key)`, отбрасывал результат, и следом
  делал `getGuideRow(key)` — но `ensureSeeded` уже возвращает ровно эту же
  строку (`return existing` в основной ветке, `return this.getGuideRow(key)`
  после наливки). Между двумя вызовами записей нет, так что второй запрос
  всегда возвращал то же самое.
- **Что изменилось для кода:** было 4 запроса к таблице `guides` на вызов,
  стало 2 (`GUIDE_KEYS` = `["user", "admin"]`). Ручка дёргается из
  `UserLayout.tsx` при каждой загрузке меню, то есть на каждый вход в
  интерфейс. Поведение идентично.
- **Как проверить:** `cd apps/api && npx nest build` — проходит. Логика:
  `ensureSeeded` — единственный источник строки, отдельного чтения не нужно.

### 4. Параллельное раскрытие дерева категорий в фильтре файлов
- **Файл:** `apps/api/src/modules/files/files.service.ts:2083-2094`
- **Зачем:** при фильтре по нескольким категориям цикл `for` делал
  `await this.getCategoryScopeIds(id)` по одному id за раз. Запросы друг от
  друга не зависят — каждый это самостоятельный рекурсивный CTE по своему
  поддереву, — но выполнялись строго последовательно.
- **Что изменилось для кода:** N выбранных категорий больше не дают N
  последовательных обращений к БД: ожидание запроса стало равно самому
  долгому из N, а не их сумме. SQL не тронут ни на символ — те же вызовы того
  же метода, изменён только порядок ожидания. Порядок заполнения `expanded`
  сохранён (`Promise.all` отдаёт результаты в порядке входного массива), а он
  и так уходит в `whereIn`, где порядок не важен.
- **Как проверить:** `cd apps/api && npx nest build` — проходит.
  В UI: расширенный поиск файлов с несколькими выбранными категориями должен
  давать тот же список, что и раньше. **Под нагрузкой на живой БД не
  проверял** — в контейнере нет docker, postgres поднять не удалось.

### 5. Удалена неиспользуемая функция `parsePagination`
- **Файл:** `apps/api/src/common/utils/pagination.ts:5-9`
- **Зачем:** её не вызывает ни один модуль — все девять сервисов
  (`files`, `users`, `sessions`, `stats`, `categories`, `sections`,
  `departments`, `positions`, `file-requests`) импортируют из этого файла
  только `buildPaginationMeta`. Разбор `page`/`pageSize` давно делает
  `PaginationDto` через `class-validator`.
- **Что изменилось для кода:** убрано 6 строк мёртвого кода и вторая,
  расходящаяся реализация лимитов пагинации: `parsePagination` резала
  `pageSize` по 100, а живой `PaginationDto` верхнего предела не имеет —
  случайный вызов старой функции дал бы тихо другое поведение.
- **Как проверить:** `cd apps/api && npx nest build`;
  `grep -rn "parsePagination" apps/api/src` — пусто.

## Не делал

- **`restoreFile`, `fetchFileActivity`, `fetchUserRequestAccessOptions`** в
  `apps/web/src/features/files/files.api.ts` и
  `apps/web/src/features/stats/stats.api.ts` — эти обёртки не вызываются из
  web, но каждой соответствует живая ручка API (например
  `POST files/:id/restore` с правом `file.restore` в
  `files.controller.ts:96`). Похоже на заготовку под ещё не собранный экран, а
  не на мусор. Уверенности не хватило — оставил.
- **`Paginated<T>` в `packages/shared/src/index.ts:11`** — не используется, но
  это публичный тип общего пакета, то есть его внешняя поверхность. Удалять
  такое в профиле «уборка» не стал.
- **`cleanupBrandingFiles` в `app-settings.service.ts:279-302`** — два цикла с
  последовательными `fs.stat`/`fs.unlink`. Формально та же «лишняя работа»,
  но вызывается только админом при сохранении брендинга и работает по
  каталогу из единиц файлов; выгода не измеримая, а диффу цена есть.
- **1.7 МБ одним бандлом** (`vite build` предупреждает про чанки >500 кБ) —
  реальная проблема, но лечится code-splitting'ом, а это уже не уборка
  лишнего, а отдельная задача с изменением загрузки приложения.
