# Поиск ошибок — e-lib-react — 2026-08-14

## Что починено

### 1. Ночная очистка корзины роняет процесс API
- **Файл:** `apps/api/src/modules/files/trash-cleanup.service.ts:16`
- **Что не так:** Обработчик `@Cron("0 3 * * *")` никто не ожидает: любое исключение
  внутри превращается в необработанное отклонение промиса, а Node 20 по умолчанию
  убивает процесс. `forceDelete` бросает `NotFoundException`, если элемент перестал
  подходить под условия выборки.
- **Когда ломается:** в 03:00 выбраны 10 файлов старше TTL; пока цикл обрабатывает
  первый, администратор восстанавливает третий (`deleted_at → null`). На третьей
  итерации `forceDelete` не находит его по `whereNotNull("deleted_at")`, бросает
  404 — промис отклоняется без `catch`, API падает и не поднимается до перезапуска
  контейнера (в проде — до `restart: unless-stopped`), а оставшиеся 7 файлов не
  вычищены. Тот же путь даёт падение при любой ошибке БД во время выборки.
- **Как починено:** тело крона обёрнуто в `try/catch`, каждая итерация цикла — в свой
  `try/catch` с записью в лог, так что сбойный элемент пропускается, а не обрывает
  сбор.

### 2. Пустой или нечисловой `TRASH_TTL_DAYS` вычищает всю корзину
- **Файл:** `apps/api/src/modules/files/trash-cleanup.service.ts:25`
- **Что не так:** `Number(this.config.get("TRASH_TTL_DAYS", "30"))` — значение по
  умолчанию срабатывает только когда переменной нет вовсе. Если она объявлена
  пустой, `Number("")` даёт `0`; если задана как `30d` — `NaN`.
- **Когда ломается:** в `.env` строка `TRASH_TTL_DAYS=` (объявлена, значение пустое) —
  `ttl = 0`, `cutoff = now`, и в 03:00 из корзины архивируются **все** удалённые
  файлы, включая удалённые минуту назад, вместо тех, что пролежали 30 дней. При
  `TRASH_TTL_DAYS=30d` получается `new Date(NaN).toISOString()` → `RangeError:
  Invalid time value` → падение процесса (см. находку 1).
- **Как починено:** значение проверяется на `Number.isFinite` и `> 0`, иначе берётся
  документированные 30 дней.

### 3. «Предыдущий период» в статистике сдвинут на сутки
- **Файл:** `apps/api/src/modules/stats/stats.service.ts:76`
- **Что не так:** `resolveRange` разбирает `YYYY-MM-DD` в часовом поясе сервера
  (`new Date("2026-08-01T00:00:00")`), а `getPreviousRange` собирает границы обратно
  через `toISOString().slice(0, 10)`, то есть в UTC.
- **Когда ломается:** сервер в `Asia/Tashkent` (UTC+5), на карточках обзора выбран
  период `from=2026-08-01`, `to=2026-08-07`. Предыдущее окно должно быть
  25.07–31.07, но `prevFrom` (25.07 00:00 местного = 24.07 19:00 UTC) печатается
  как `2026-07-24`, а `prevTo` — как `2026-07-30`. Сравнение идёт с окном
  24.07–30.07: 31 июля не учтено, 24 июля учтено лишний раз, и дельта
  «к предыдущему периоду» показывает неверные цифры при каждом открытии страницы.
- **Как починено:** добавлен `formatLocalDate`, границы предыдущего окна печатаются
  теми же локальными компонентами даты, какими их читает `resolveRange`.

### 4. Заявка на публикацию обрабатывается дважды
- **Файл:** `apps/api/src/modules/files/file-requests.service.ts:792`
- **Что не так:** `approveRequest` / `approveUpdateRequest` читают `status` отдельным
  запросом до транзакции, а переводят его в `approved` в самом конце. Между чтением
  и записью статус ничем не защищён.
- **Когда ломается:** администратор дважды нажимает «Одобрить» (кнопка блокируется
  только по `isPending` своей мутации — второй клик из другой вкладки или с другого
  аккаунта проходит), либо два администратора разбирают очередь одновременно. Оба
  запроса видят `status = "pending"`, оба создают `file_items` + `file_versions` +
  `file_version_assets` — в библиотеке появляются два документа, ссылающиеся на один
  и тот же файл на диске. Для заявки на обновление тем же путём создаются две версии
  с одинаковым `version_number`.
- **Как починено:** статус переводится первым же действием внутри транзакции
  запросом `where({ id, status: "pending" }).update(...)`; проигравший видит 0
  изменённых строк, получает `BadRequestException` и откатывается — блокировка
  строки в Postgres сериализует конкурентов.

### 5. Отмена заявки удаляет файл только что опубликованного документа
- **Файл:** `apps/api/src/modules/files/file-requests.service.ts:762`
- **Что не так:** `cancelRequest` и `rejectRequest` проверяют `status` до записи, а
  затем `deleteRequestAssets` физически удаляет файлы с диска. Одобрение при этом
  переносит **те же самые пути** в `file_version_assets` (файл не копируется).
- **Когда ломается:** пользователь открывает свои заявки и жмёт «Отменить» в тот
  момент, когда администратор жмёт «Одобрить». Обе операции видят `pending`;
  одобрение публикует документ с путём `uploads/2026/08/14/prikaz.pdf`, отмена
  следом делает `unlink` этого пути. В базе документ есть и виден в библиотеке, а
  при скачивании `res.download` не находит файл — документ навсегда битый.
- **Как починено:** переход в `canceled` / `rejected` выполняется тем же охраняемым
  `update ... where status = 'pending'`; если заявку уже одобрили, удаление файлов
  не запускается вовсе.

## Не чинил

- **`PASSWORD_MAX_LENGTH = 128` при 72-байтном пределе bcrypt**
  (`apps/api/src/common/validators/password.ts:6`). Комментарий рядом обещает
  «cap well before that», но пароль длиннее 72 байт молча обрезается, и войти можно
  по его началу. Правка меняет политику паролей и может закрыть вход уже
  существующим пользователям с длинным паролем — это решение владельца проекта, а не
  бота.
- **`pageSize` без верхней границы** в `PaginationDto` (`@Min(1)` есть, `@Max` нет):
  `GET /api/user/files?pageSize=1000000` тянет всю таблицу в память. Ограничение
  меняет контракт API и поведение экспорта — вынес отдельно.
- **`imageParagraphs` при нулевой ширине картинки**
  (`apps/api/src/modules/guides/guide-docx.ts:91`): у битого PNG с `width = 0`
  получается деление на ноль и `NaN` в размерах DOCX. Не нашёл входных данных из
  реального потока загрузки, при которых это воспроизводится, — только
  вручную собранный файл.
- **Гонка двух одобрений на уровне файлов на диске:** после правки 4 дубликат
  документа не создаётся, но общая схема «путь к файлу переиспользуется, а не
  копируется» осталась. Полный переход на копирование ассета при публикации — это
  уже переделка, а не починка дефекта.
