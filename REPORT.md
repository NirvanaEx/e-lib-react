# Уязвимости — e-lib-react — 2026-08-16

## Что сделано

### 1. Потолок на `pageSize` во всех списках

- **Файл:** `apps/api/src/common/dto/pagination.dto.ts:9-23`
- **Зачем:** у `pageSize` был только `@Min(1)`, верхней границы не было.
  Размер страницы приходит прямо из query-строки и передаётся в `.limit()`
  без ограничения — любой вошедший пользователь мог заставить API вытащить,
  склеить и сериализовать всю таблицу целиком. От этого DTO наследуются все
  списочные запросы: файлы, пользователи, аудит, сессии, подразделения,
  должности, разделы, категории, заявки, корзина.
- **Как эксплуатируется:** обычный пользователь (роль `user`, право
  `file.read`) шлёт
  `GET /api/user/files?page=1&pageSize=1000000` с сессионной кукой.
  Обработчик `listUserFiles` снимает `LIMIT 1000000`, а затем на каждую
  полученную строку доборными запросами тянет переводы и ассеты
  (`files.service.ts:2170-2270`), после чего складывает всё в JSON в памяти.
  Глобальный throttler разрешает 300 запросов в минуту, так что нескольких
  параллельных ссылок хватает, чтобы выесть память и процессор процесса API.
  Тот же приём работает и на `GET /api/dashboard/audit?pageSize=10000000`,
  и на остальных списках.
- **Что изменилось для пользователя или для кода:** запрос со страницей
  больше 1000 строк отвергается с 400 ещё в ValidationPipe; сам фронт
  максимум просит 1000 (полный список избранного на главной и в библиотеке),
  так что интерфейс не задет. Экспорт статистики лимит в DTO не проходит —
  он ставит `EXPORT_ROW_LIMIT` внутри контроллера и работает как прежде.
- **Как проверить:** `npm run build --workspace apps/api`, затем при
  поднятом API: `curl -i -b "access_token=<кука>" "http://localhost:3001/api/user/files?pageSize=1000000"`
  → `400 Bad Request` (`pageSize must not be greater than 1000`);
  `...?pageSize=1000` → `200`. В браузере: главная, «Общая библиотека»,
  «Избранное», журнал аудита — списки и пагинация работают как раньше.

### 2. Перечисление логинов по времени ответа `/auth/login`

- **Файл:** `apps/api/src/modules/auth/auth.service.ts:21-27, 178-180`
- **Зачем:** текст ошибки для несуществующего и существующего логина был
  одинаков (это в коде сделано намеренно), но время — нет. При неизвестном
  логине функция выходила сразу после `SELECT`, а при известном платила за
  `bcrypt.compare` (cost 10, ~100 мс). Разница на два порядка — готовый
  оракул, который отличает заведённые учётные записи от незаведённых, а
  блокировка после 5 неудач ему не мешает: она наступает уже после ответа,
  и время ответа с «locked» тоже отличается от времени обычного отказа.
- **Как эксплуатируется:**
  `curl -o /dev/null -s -w "%{time_total}\n" -X POST http://<host>/api/auth/login -H 'Content-Type: application/json' -d '{"login":"ivanov","password":"x"}'`
  → ~0.1 с, если `ivanov` существует, и ~0.005 с, если нет. Прогнав так
  список фамилий сотрудников (логины в системе строятся из них), атакующий
  получает точный перечень действующих учётных записей и дальше распыляет
  пароли только по ним, укладываясь в лимит попыток на аккаунт.
- **Что изменилось для пользователя или для кода:** при неизвестном логине
  пароль теперь сверяется с заведомо неподходящим хешем той же стоимости,
  поэтому обе ветки отвечают за сравнимое время. Ответ, код и запись в
  `login_attempts` прежние.
- **Как проверить:** `npm run build --workspace apps/api`; при поднятом API
  сравнить `time_total` двух запросов выше — теперь оба порядка 0.1 с.
  Обычный вход и блокировка после 5 неудач не изменились.

## Не делал

- **Названия файлов с ограниченным доступом видны всем в общей библиотеке.**
  `listUserFiles` (`files.service.ts:2046-2310`) намеренно отдаёт все файлы
  кроме `department_closed` и помечает недоступные флагом `canDownload`;
  скачивание при этом закрыто `validateAccess`. Это выглядит осознанным
  решением продукта, а не дырой; менять поведение без подтверждения не стал.
- **Вечная блокировка учётной записи.** Каждая неудачная попытка, включая
  отбитые по блокировке, продлевает окно (`getLockoutSeconds`), так что
  атакующий может держать чужой (в том числе `superadmin`) аккаунт
  заблокированным, стуча раз в несколько секунд. Это неотъемлемая цена
  выбранной схемы lockout — лечится не заплаткой, а отдельным решением
  (капча, окно без продления), и его стоит принимать хозяину проекта.
- **`AUTH_COOKIE_SECURE=false` в `.env.example`** — кука аутентификации
  поедет по открытому HTTP, если прод настроен по образцу. Это файл
  конфигурации развёртывания, трогать его правилами прогона запрещено;
  выношу как замечание.
- **Отсутствие `@Throttle` на `POST /api/user/settings/password`.** Смена
  пароля с проверкой текущего живёт только под общим лимитом 300/мин, в
  отличие от `change-temp-password`. Внятного сценария эксплуатации написать
  не смог (нужна уже угнанная сессия), поэтому оставил.
- Не проверял: содержимое `.env` и рабочего прод-окружения, миграции и
  `ops/` — по правилам прогона.
