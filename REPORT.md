# Уязвимости — e-lib-react — 2026-08-14

## Что сделано

### 1. Неограниченный `pageSize` во всех постраничных запросах

- **Файл:** `apps/api/src/common/dto/pagination.dto.ts:11`
- **Зачем:** У `pageSize` стоял только `@Min(1)`, верхней границы не было.
  Значение из строки запроса попадало напрямую в `.limit(pageSize)` — без
  промежуточного клампа. От `PaginationDto` наследуются 11 DTO
  (`FilesQueryDto`, `UsersQueryDto`, `AuditQueryDto`, `SessionsQueryDto`,
  `ActivityQueryDto`, `TrashQueryDto` и другие), то есть дыра была во всех
  постраничных ручках сразу — и в пользовательских, и в панельных.
  Соседний `TopQueryDto.limit` в этом же проекте ограничен `@Max(50)`, так что
  это именно пропуск, а не осознанное решение. Функция `parsePagination()`
  в `common/utils/pagination.ts`, которая режет размер до 100, нигде не
  вызывается — мёртвый код, защиты не давал.
- **Что изменилось для пользователя или для кода:** `pageSize` больше 1000
  теперь отклоняется валидатором с 400; всё, что реально запрашивает фронт,
  проходит без изменений. Потолок выбран равным 1000, потому что это самая
  большая страница, которую просит SPA (список избранного —
  `UserFilesPage.tsx:183` и `UserHomePage.tsx:75`); следующие по величине
  запросы — 500 и 200.
- **Как эксплуатируется:** любой аккаунт с самой низкой ролью `user` (нужно
  только право `file.read`) шлёт один запрос:

  ```
  GET /api/user/files?pageSize=100000000
  Authorization: Bearer <любой валидный токен>
  ```

  До правки Postgres выполнял `LIMIT 100000000` по `file_items` с четырьмя
  join'ами переводов и версий, отдавал всю таблицу, после чего сервис
  дособирал результат в JS и сериализовал его в JSON. Один дешёвый для
  атакующего запрос съедает память и CPU процесса API; несколько параллельных
  кладут его. Глобальный троттлер (300 запросов в минуту) от этого не спасает —
  хватает и единиц. Тот же приём работал на `/api/dashboard/audit`,
  `/api/dashboard/users`, `/api/user/requests` и остальных постраничных ручках.
  После правки запрос получает `400 Bad Request` с сообщением
  `pageSize must not be greater than 1000`.
- **Как проверить:**
  ```bash
  npx tsc --noEmit -p apps/api/tsconfig.json   # проходит без ошибок
  ```
  Поведение валидатора проверено прогоном `plainToInstance` + `validateSync`
  на самом `PaginationDto` (временный скрипт, удалён после проверки):

  ```
  {"pageSize":"20"}        -> accepted pageSize=20
  {"pageSize":"1000"}      -> accepted pageSize=1000
  {"pageSize":"1001"}      -> REJECTED (pageSize must not be greater than 1000)
  {"pageSize":"100000000"} -> REJECTED (pageSize must not be greater than 1000)
  {}                       -> accepted pageSize=20
  ```

  В браузере: открыть «Все файлы», «Избранное», «Журнал» и «Пользователи» —
  выдача и пагинация прежние.

## Не делал

- **`page` без верхней границы.** `offset((page - 1) * pageSize)` принимает
  сколь угодно большой номер страницы. Postgres отбрасывает строки до
  смещения, но при пустом хвосте выходит быстро, и внятного сценария с
  измеренной деградацией я не построил. Это подозрение, а не находка — по
  правилам отчёта ему место здесь. С ограниченным `pageSize` цена запроса в
  любом случае упала.
- **Длина `q` в поиске.** Параметр `q` не ограничен по длине и уходит в
  `ILIKE '%...%'` по трём объединённым подзапросам (`files.service.ts:837,
  859, 885`). Значение параметризовано, инъекции нет; насколько дорога очень
  длинная строка — не мерил, поэтому не трогал.
- **Мёртвый `parsePagination()`** (`common/utils/pagination.ts:5`). Функция
  клампит до 100 и не вызывается ниоткуда — читается как защита, которой нет.
  Удаление — уборка, а не закрытие уязвимости, и по правилам прогона это шум
  в диффе. Оставил следующему проходу.

  Проверено и признано чистым (правок не потребовалось): SQL везде
  параметризован, `${direction}` в `orderByRaw` берётся из белого списка
  (`sortDir === "asc" ? "asc" : "desc"`); отдача файлов (`branding.public`,
  `guides/image`, аватары) закрыта `path.basename` плюс белым списком
  расширений; загрузки пишутся под сгенерированными именами с проверкой
  MIME, расширения и размера; `validateAccess()` вызывается во всех четырёх
  пользовательских ручках файлов, включая скачивание версий; повышение прав
  прикрыто `assertCanManageRole` и отдельной проверкой на `superadmin`;
  кука `httpOnly` + настраиваемые `secure`/`SameSite`; CORS в проде закрыт по
  умолчанию; `X-Forwarded-For` учитывается только при явном `TRUST_PROXY`;
  экспорт CSV экранирует формулы; `JWT_SECRET` обязателен и не может быть
  `change_me`, отзыв токенов через `token_version`; катастрофических
  регулярок и `eval`/`dangerouslySetInnerHTML` не нашёл.
