# Уязвимости — e-lib-react — 2026-08-14

## Что починено

### 1. Закрытые файлы чужого отдела читаются через «Избранное»
- **Файл:** `apps/api/src/modules/files/files.service.ts:1487` (`addFavorite`), `apps/api/src/modules/files/files.service.ts:1269` (`listUserFavorites`)
- **Что не так:** `addFavorite` проверял только существование `file_items` и отсутствие
  `deleted_at`, а `listUserFavorites` выбирал избранное вообще без фильтра доступа.
  Тип `department_closed` по замыслу (`OPEN_ACCESS_TYPES`, комментарий в
  `files.service.ts:16-27`) не показывается ни в общей библиотеке
  (`listUserFiles` явно делает `whereNot access_type = department_closed`), ни в меню
  (`getUserMenu` фильтрует по `file_access_departments`/`file_access_users`), и
  `validateAccess` не пускает к нему на скачивание. Избранное было обходной дорогой:
  идентификатор файла — единственное, что требовалось.
- **Когда ломается:** обычный пользователь отдела Б с правом `file.read`:
  1. `POST /api/user/favorites/42`, где 42 — id файла отдела А с `access_type = department_closed`
     (id перебирается: 1, 2, 3, …; несуществующие дают 404, чужие закрытые давали 200);
  2. `GET /api/user/favorites` → в ответе объект этого файла с `title`, `description`,
     `availableLangs`, `availableAssetExts`, `currentAssetSize`, `sectionId`, `categoryId`.
  То есть наружу утекали названия, описания и состав закрытых документов чужого отдела.
  Само содержимое файла не отдавалось — `download` защищён `validateAccess`.
- **Как починено:** `addFavorite` отказывает с 403, если файл `department_closed`, а у
  пользователя нет доступа по отделу (или права `file.download.restricted`), и
  `listUserFavorites` дополнительно отфильтровывает такие файлы — чтобы записи,
  добавленные до правки или после перевода пользователя в другой отдел, тоже перестали
  светиться.

### 2. `pageSize` без верхней границы
- **Файл:** `apps/api/src/common/dto/pagination.dto.ts:20`
- **Что не так:** у `pageSize` был только `@Min(1)`. Значение уходило прямо в
  `.limit(pageSize)` во все списковые запросы (`listUserFiles`, `list` пользователей,
  `listAdminRequests`, аудит, сессии и т. д.), а следом код строит по всем полученным
  строкам `whereIn(...)`-подзапросы и Map’ы в памяти процесса.
- **Когда ломается:** любой вошедший пользователь с `file.read` шлёт
  `GET /api/user/files?pageSize=100000000` (или в несколько потоков) — Postgres отдаёт
  всю таблицу, Node строит объекты по каждой строке и делает добор ассетов и переводов
  по всем id. Память API растёт линейно от размера базы, процесс уходит в OOM.
  Ограничение `client_max_body_size` в nginx тут не помогает: это GET-запрос.
- **Как починено:** добавлен `@Max(1000)` — это ровно тот потолок, который уже
  запрашивают самые «жадные» экраны фронта (`UserFilesPage`, `UserHomePage` шлют 1000),
  так что рабочие сценарии не меняются, а запрос на миллион строк отклоняется валидацией.

## Не чинил

- `GET /api/users/:id/avatar` отдаёт аватар любого пользователя по id любому вошедшему —
  похоже на задумку (аватары показываются в карточках файлов и заявок), персональных
  данных сверх картинки не отдаётся. Не находка, а вопрос к продуктовому решению.
- `TRUST_PROXY` по умолчанию выключен, при этом прод стоит за nginx, который проставляет
  `X-Forwarded-For`. Если переменная не задана в `.env`, все запросы приходят с одного
  адреса и общий IP-лимит блокировок логина (`IP_ATTEMPT_MULTIPLIER`) начинает срабатывать
  на всех сразу. Это настройка деплоя (`.env` трогать нельзя), и сама по себе она
  ужесточает, а не ослабляет защиту — оставил.
- `listUserFiles` показывает названия файлов с `access_type = restricted` всем
  пользователям, помечая их `canDownload: false`. Судя по комментариям и по тому, что
  этот флаг явно вычисляется, так и задумано. Уверенности, что это дефект, нет —
  не трогал.
- Ветка `restricted_open` в `normalizeAccess` (`file-requests.service.ts:106`) позволяет
  автору заявки сделать файл читаемым всем, указав только свой отдел. Поведение описано в
  комментарии как намеренное; экплойта, выходящего за рамки задуманного, сформулировать не
  смог.
- Аудит фронта на XSS сделан поверхностно: `dangerouslySetInnerHTML`/`innerHTML` в
  `apps/web/src` нет, тексты инструкций рендерятся через `Typography`. Более глубокий
  разбор рендеринга брендинга (`sanitizeBranding`) не делал — не хватило объёма прогона.
