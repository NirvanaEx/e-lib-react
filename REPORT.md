# Уборка лишнего — e-lib-react — 2026-08-14

## Что починено

### 1. Два неиспользуемых макета панели
- **Файл:** `apps/web/src/app/layouts/AdminLayout.tsx`, `apps/web/src/app/layouts/ManageLayout.tsx`
- **Что не так:** оба компонента экспортируются по умолчанию, но не импортируются
  нигде: `App.tsx` строит все маршруты `/dashboard/*` через `DashboardLayout`, а
  пользовательские — через `UserLayout`. Это прежние жёсткие списки пунктов меню,
  вытесненные `DashboardLayout` с фильтрацией по правам.
- **Когда ломается:** не ломается — код мёртвый; он вводит в заблуждение при
  правке навигации (пункты в `AdminLayout`/`ManageLayout` уже разошлись с тем,
  что реально показывает `DashboardLayout`).
- **Как починено:** оба файла удалены.
- **Выгода:** убрано 49 строк мёртвого кода; вариантов «где заводится пункт меню»
  стало один вместо трёх.

### 2. Мёртвая раскладка таблицы `userLibraryTableLayouts`
- **Файл:** `apps/web/src/features/files/fileTableLayout.ts:100`
- **Что не так:** объект с тремя наборами колонок (`files`, `department`,
  `favorites`) не импортируется ни одним файлом. `UserLibraryPage.tsx` вообще не
  ссылается на модуль раскладок, а `UserFilesPage.tsx` использует
  `sharedLibraryTableLayout` — почти идентичный набор, оставшийся после
  объединения таблиц.
- **Когда ломается:** не ломается — код мёртвый; при правке ширин колонок его
  легко принять за действующий и править впустую.
- **Как починено:** блок `userLibraryTableLayouts` удалён целиком, действующие
  `adminFilesTableLayout` и `sharedLibraryTableLayout` не тронуты.
- **Выгода:** убрано 146 строк мёртвого кода, файл сократился с 245 до 98 строк.

### 3. Мёртвая функция `parsePagination`
- **Файл:** `apps/api/src/common/utils/pagination.ts:5`
- **Что не так:** функция не вызывается нигде — разбор `page`/`pageSize` давно
  делает `PaginationDto` через `class-transformer`/`class-validator`. Из этого же
  модуля используется только `buildPaginationMeta` (10 вызовов).
- **Когда ломается:** не ломается — код мёртвый; но он задаёт свой предел
  `pageSize` (100), который расходится с DTO, так что при правке лимита правка
  сюда попадёт впустую.
- **Как починено:** функция удалена, `buildPaginationMeta` оставлен.
- **Выгода:** убрано 5 строк мёртвого кода; правил разбора пагинации осталось
  одно место вместо двух.

### 4. Рекурсивный обход дерева категорий по одному запросу на категорию
- **Файл:** `apps/api/src/modules/files/files.service.ts:2083`
- **Что не так:** в `listUserFiles` фильтр «категории» из расширенного поиска
  раскрывался циклом: на каждый выбранный id — отдельный `WITH RECURSIVE` запрос,
  причём последовательно (`await` внутри `for`), хотя запросы независимы.
- **Когда ломается:** не ломается, но делает лишнюю работу: при запросе
  `GET /user/files?categoryIds=1,2,3,4,5` — 5 рекурсивных обходов дерева
  категорий подряд перед основным запросом; при выборе 12 категорий — 12.
- **Как починено:** добавлен `getCategoriesScopeIds`, который засевает тот же
  `WITH RECURSIVE` сразу всеми id (`WHERE id IN (?, ?, …)`, `SELECT DISTINCT`), и
  цикл заменён одним вызовом.
- **Выгода:** было N последовательных рекурсивных запросов на страницу списка
  (N = число выбранных категорий), стал один независимо от N.

**Эквивалентность правки 4.** Прежний код для существующей категории добавлял в
набор её поддерево (сам id входит в него как корень CTE), а для несуществующей —
голый id. Новый набор — объединение результата общего обхода со списком самих
`filterCategoryIds`: для существующих id добавление дубля ничего не меняет, для
несуществующих воспроизводит прежнюю ветку `else`. Итоговый `whereIn` тот же.

## Не чинил

- `restoreFile`, `fetchUserRequestAccessOptions` (`files.api.ts`),
  `fetchFileActivity` (`stats.api.ts`) — обёртки над реально существующими
  ручками API, вызовов из компонентов нет. По 3–4 строки каждая; похоже на
  намеренно поддерживаемую поверхность клиента, выгоды от удаления не
  сформулировать — оставил.
- `GuidesService.listStatuses` (`apps/api/src/modules/guides/guides.service.ts:178`)
  — цикл по двум ключам инструкций, 4 запроса вместо возможного одного. Выигрыш
  фиксированный и маленький (ключей ровно 2), а свести в один запрос мешает
  `ensureSeeded` с первичным наливом из поставки — риск выше выгоды.
- Экспортированные типы, используемые только внутри своего файла
  (`PublicSettings`, `AuditLogInput`, `JwtPayload`, `ActivityRow` и ещё около
  двадцати) — это изменение публичной поверхности модулей ради нуля строк
  выполняемого кода, шум в диффе.
- Последовательные `await uploadAsset(...)` в циклах загрузки файлов
  (`FilesPage.tsx:462`, `FileDetailsPanel.tsx`, `UserLibraryPage.tsx`) —
  операции независимы, но это загрузка файлов на сервер; последовательность
  может быть намеренной (порядок версий, нагрузка). Уверенности нет.
