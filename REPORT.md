# Поиск ошибок — e-lib-react — 2026-08-16

## Что сделано

### 1. Двойное одобрение заявки создаёт документ-дубль

- **Файл:** `apps/api/src/modules/files/file-requests.service.ts:790` (`assertStillPending`, вызовы в `approveRequest` и `approveUpdateRequest`)
- **Зачем:** статус заявки проверялся вне транзакции (`if (request.status !== "pending")`), а менялся на `approved` только в самом её конце. Между этими двумя моментами лежат чтение переводов, вложений, прав доступа и вставка нескольких таблиц — то есть десятки миллисекунд. **Когда ломается:** администратор дважды кликает «Одобрить» на карточке заявки (или два администратора разбирают очередь одновременно) — второй запрос проходит проверку `pending`, пока первый ещё внутри транзакции, и в библиотеке появляются две карточки на одну заявку. Обе строки `file_version_assets` указывают на **один и тот же файл на диске**: удаление одного документа физически уносит файл второго, и он начинает отдавать 404 при скачивании. В варианте «обновление файла» тем же путём создаются две версии с одинаковым `version_number`.
- **Что изменилось для пользователя или для кода:** внутри транзакции строка заявки блокируется `SELECT ... FOR UPDATE` и статус перечитывается; второй запрос ждёт на блокировке и после коммита первого получает 400 «Request is not pending» вместо дубля.
- **Как проверить:** отправить два `POST /api/dashboard/file-requests/:id/approve` одновременно (`curl ... & curl ...`) — первый вернёт `fileItemId`, второй 400; в `file_items` появится ровно одна запись. Не запускал: для этого нужны поднятые Postgres и API с реальной заявкой, окружения под рукой нет.

### 2. Отклонение заявки стирало файлы уже одобренного документа

- **Файл:** `apps/api/src/modules/files/file-requests.service.ts:1107` (`rejectRequest`), `:772` (`cancelRequest`), общий помощник `resolvePending` на `:800`
- **Зачем:** `rejectRequest` и `cancelRequest` делали безусловный `UPDATE ... WHERE id = ?`, а затем `deleteRequestAssets` — физический `unlink` вложений. **Когда ломается:** администратор нажимает «Отклонить», пока одобрение той же заявки уже выполняется (двойной клик по разным кнопкам, или один разбирает, другой отклоняет). Одобрение успевает перенести пути вложений в `file_version_assets`, после чего отклонение удаляет эти файлы с диска — документ в библиотеке остаётся, а скачивание падает.
- **Что изменилось для пользователя или для кода:** переход в конечный статус делается одним условным `UPDATE ... WHERE id = ? AND status = 'pending'`; если строк не затронуто (заявку уже разобрали), возвращается 400, и удаление файлов не выполняется.
- **Как проверить:** параллельно `approve` и `reject` одной заявки — ровно одна операция завершится успехом, файл одобренного документа останется на диске. Не запускал по той же причине, что и п. 1.

### 3. Ночная уборка корзины валила весь API

- **Файл:** `apps/api/src/modules/files/trash-cleanup.service.ts:20`
- **Зачем:** у `@Cron`-метода нет вызывающего, и отклонённый промис становится `unhandledRejection`, а это в Node ≥ 15 остановка процесса, а не одна проваленная уборка. **Когда ломается:** (а) элемент восстановили из корзины между `SELECT` списка и вызовом `forceDelete` — тот кидает `NotFoundException`, и API падает в 03:00; (б) `TRASH_TTL_DAYS` в `.env` пустой или задан как `30d` — `Number()` даёт `NaN`, `new Date(NaN).toISOString()` кидает `RangeError` в первой же строке задачи, и API падает при первом же срабатывании крона. Заодно `TRASH_TTL_DAYS=` (пустая строка) давало `Number("") === 0`, то есть cutoff «сейчас» — корзина вычищалась бы целиком и молча.
- **Что изменилось для пользователя или для кода:** тело задачи обёрнуто в `try/catch` с логированием, каждый элемент удаляется в собственном `try/catch` (сбой одного не обрывает остальные), нечисловой и неположительный TTL откатывается к 30 дням.
- **Как проверить:** `TRASH_TTL_DAYS=abc npm run start --workspace apps/api` и дождаться срабатывания крона (или временно поменять выражение на `* * * * *`) — в логе будет `Trash cleanup failed: ...`, процесс останется жив. Не запускал: нужен поднятый Postgres.

### 4. Первое открытие инструкций отдавало 500

- **Файл:** `apps/api/src/modules/guides/guides.service.ts:106` (`writeBlocks`)
- **Зачем:** инструкция из поставки разворачивается лениво, при первом обращении (`ensureSeeded`), а `guides.key` — уникальный индекс. **Когда ломается:** сразу после деплоя/миграции первая же загрузка интерфейса шлёт `GET /api/guides` (статусы для меню) и `GET /api/guides/user` (сама страница) параллельно; обе транзакции видят пустую таблицу и делают `INSERT` — вторая падает на нарушении уникальности, пользователь получает 500. Достаточно двух одновременных пользователей после обновления.
- **Что изменилось для пользователя или для кода:** вставка идёт через `onConflict("key").ignore()`, после чего строка перечитывается, а её блоки переписываются заново — повторный заход не плодит дублей и не роняет запрос.
- **Как проверить:** на чистой базе выполнить два параллельных `GET /api/guides/user` — оба вернут 200, в `guides` будет одна строка на ключ. Не запускал: нужна чистая база.

### 5. Незагруженное вложение оставалось на диске навсегда

- **Файл:** `apps/api/src/modules/files/files.service.ts:1852` (`uploadAsset`)
- **Зачем:** multer пишет файл на диск **до** входа в обработчик, а `if (!version) throw new NotFoundException()` выходил, не убрав его. Все остальные ветки отказа в этом же методе (размер, расширение, MIME) файл убирают — эта была пропущена. **Когда ломается:** загрузка вложения в версию, которую только что удалили в соседней вкладке, или запрос с чужим `versionId` — в корне `UPLOAD_DIR` остаётся `.tmp`-файл, который ничем не подчищается; повторяемо и добивается до конца диска.
- **Что изменилось для пользователя или для кода:** перед 404 временный файл удаляется тем же `deleteFileSafe`, что и в остальных ветках.
- **Как проверить:** `POST /api/dashboard/files/:id/versions/999999/assets` с любым файлом → 404, в `UPLOAD_DIR` не появляется `*.tmp`. Не запускал: нужен поднятый API.

## Не делал

- **`getPreviousRange` в `stats.service.ts:65` сравнивает даты через `toISOString()`.** Границы диапазона строятся как локальная полночь (`new Date("2026-08-01T00:00:00")`), а обратно форматируются в UTC — при `TZ` восточнее Гринвича «предыдущий период» на дашборде съезжает на сутки. В проде контейнеры идут без `TZ`, то есть в UTC, где расчёт верен; ломается только при явно выставленном `TZ`. Оставил: в проде сейчас не проявляется, а править — значит трогать формат всех дат в модуле.
- **`readImageSize` может вернуть нулевые размеры** (`guide-image-size.ts:8`): для битого PNG/JPEG с шириной 0 в `guide-docx.ts:88` получается `height = NaN`, и DOCX уезжает с некорректной картинкой. Не чинил: не нашёл, чтобы такие файлы реально проходили загрузку, — сценария из прода нет.
- **`buildDownloadName` падает на `original_name = null`** (`files.user.controller.ts:174`): `path.parse(null)` кидает `TypeError` → 500 вместо файла. Колонка `not null`, воспроизвести на живых данных не смог — оставил следующему прогону.
- **Второй `useEffect` в `useAuth.tsx:105` пересоздаёт слушатели и интервал на каждый ответ `me()`** (в зависимостях `user`, а `setAuth` кладёт новый объект). Утечки нет — cleanup срабатывает, — но 60-секундный таймер перезапускается при каждом фокусе окна. Это уже поведение, а не поломка, и правка задевает порядок обновления профиля.
- **`pageSize` не ограничен сверху** в `PaginationDto` и в контроллерах (`query.pageSize || 20`): запрос с `pageSize=1000000` тянет всю таблицу. Не чинил — это про нагрузку, а не про конкретный сломанный сценарий.
